# 通用代码质量规则

## 1. 正确性先于美观

优化前先确认现有行为和任务目标。不要因为某种写法“更优雅”就改变：

- API 请求/响应契约
- 异常类型或错误码
- 数据库事务语义
- 排序、分页、空值语义
- 重试、超时、幂等行为
- 序列化格式
- 对外可见日志或事件语义（如果被系统依赖）

纯重构优先保持行为；想改变行为时必须与用户目标一致。

## 2. 减少认知负担

判断重构是否真的更好，不看“类更多/方法更短”，而看读者需要同时理解多少概念。

优先：

- 早返回替代深层嵌套。
- 删除无价值转发层。
- 合并重复条件与重复计算。
- 明确不变量和类型边界。
- 把相关逻辑放在一起。
- 让名称表达业务意义。

谨慎：

- 单一实现的接口。
- 只调用一次、仅搬运几行代码的 helper。
- 只为了模式完整而出现的 Factory/Strategy/Builder。
- “以后可能会用”的扩展点。

## 3. 命名

- 名称表达业务角色，而不是数据类型或临时状态。
- 避免 `data`、`info`、`obj`、`tmp`、`result1`、`handleData` 等上下文不足的名称。
- boolean 应体现判断含义，如 `isActive`、`hasPermission`、`shouldRetry`。
- 同一概念使用同一术语，不在相邻模块中随意使用同义词。
- 不用注释弥补糟糕命名；先改名。

## 4. 函数与方法

函数应有清晰职责，但“短”不是目的。

应该拆分：

- 同时处理多个独立业务步骤。
- 需要在多个地方复用同一稳定规则。
- 某段逻辑可以用业务名称替代复杂实现细节。
- 测试边界更清晰。

不应拆分：

- 只是为了让主函数看起来短。
- 新函数只有一两行转发，名称没有增加信息。
- 调用链因此增加但理解成本没有下降。

## 5. 条件与控制流

- 优先处理失败/特殊情况并提前返回。
- 避免超过必要层数的嵌套。
- 同一种对象反复出现相同条件判断，检查是否缺少明确状态模型或集中策略。
- 不要把与当前流程无关的新条件硬塞进通用逻辑。
- 复杂 boolean 表达式可用有业务意义的局部变量或谓词表示。

## 6. 重复逻辑

不是任何重复都要抽象。

适合抽象：

- 相同业务规则在多处重复。
- 修改其中一处时其他地方必须同步修改。
- 已经存在稳定 canonical helper。

不适合抽象：

- 两段代码只是暂时长得像，但业务语义不同。
- 为了消灭 2~3 行重复引入复杂参数、回调或继承结构。

## 7. 错误处理

- 不吞异常。
- 异常信息保留必要上下文，但不泄露敏感信息。
- 不用异常作为常规分支逻辑。
- 在能真正处理/转换/补充上下文的边界捕获异常。
- 重试必须考虑次数、退避、幂等、超时和不可重试错误。

## 8. 外部 I/O

数据库、网络、文件、进程调用比纯计算更值得关注：

- 避免循环中逐个远程调用/查询，优先批量或并行（在语义允许时）。
- 明确超时。
- 明确资源关闭。
- 列表/搜索接口考虑分页或上限。
- 对失败、部分失败、空结果有清晰语义。

## 9. 依赖

新增依赖前检查：

- 标准库或现有依赖是否已经能解决。
- 新依赖是否真的显著降低复杂度。
- 维护状态、许可证、安全风险、包体积/运行时成本是否可接受。

不要为了几行简单逻辑新增大型依赖。

## 10. 注释

注释解释：

- 为什么必须这样做。
- 不明显的业务约束。
- 外部系统限制。
- 容易误删的兼容性原因。

不要注释：

- 代码本身已经明显表达的动作。
- 已删除代码的历史痕迹。
- 与实现不同步的设计幻想。
