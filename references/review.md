# Code Review 工作流

## 五个审查轴

### 1. Correctness

- 是否满足任务/规格？
- 空值、空集合、边界值、错误路径是否正确？
- 是否有状态不一致、竞态、资源泄漏？
- 测试是否真的覆盖行为，而不是只覆盖实现细节？

### 2. Readability & Simplicity

- 命名是否能脱离作者解释独立理解？
- 控制流是否直观？
- 有没有炫技或不必要的链式/元编程？
- 新抽象是否真的降低认知负担？
- 重构是减少复杂度，还是只是把复杂度搬到更多文件？

### 3. Architecture

- 是否遵循现有模块边界？
- 依赖方向是否合理？
- feature-specific 逻辑是否泄漏到共享模块？
- 是否重复实现已有 canonical helper？
- 是否为了本次需求引入过大的架构变化？

### 4. Security

- 外部输入是否在边界验证？
- 鉴权/授权是否遗漏？
- 是否有 SQL/命令/路径/XSS 等注入风险？
- 是否泄露 secret 或隐私数据？

### 5. Performance

- N+1 / 循环 I/O？
- 无界查询/循环/并发？
- 前端 waterfall / 重复请求 / 大 bundle / 无意义 rerender？
- 优化建议是否有足够证据？

## Finding 格式

优先写少而高价值的发现。

示例结构：

```text
Required — OrderService.java:128
问题：在 200 个订单循环中逐条查询用户信息，会形成 N+1。
影响：请求延迟和数据库压力随订单数线性放大。
建议：先收集 userId，一次批量查询并构建 Map，再在循环中 O(1) 查找。
```

## 严重度

- **Critical**：安全漏洞、数据损坏、核心功能错误。
- **Required**：应在合并前修复的正确性/结构/高风险问题。
- **Consider**：有明确收益，但当前不修也可接受。
- **Nit**：纯风格偏好；少用。

## 不要做的 Review

- 只报 formatter 能自动修的问题。
- 因为“我会这样写”就要求改写。
- 把所有建议都标 Required。
- 对没有证据的性能问题做确定性判断。
- 明知存在核心结构问题，却列十几个低价值命名 Nit 把重点淹没。
- 为了显得有输出，在没有问题时硬找问题。
